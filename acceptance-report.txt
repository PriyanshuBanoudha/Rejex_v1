----------------------------------------------------------------------------------------------------
SUITE T1: CORE SERVICES, AUTHENTICATION & TEAM LIFECYCLE
----------------------------------------------------------------------------------------------------
Objective: Validate system health endpoints, dual-JWT user authentication with Argon2id password 
hashing, role-based route access, event creation workflows, team invitations, and OpenAPI spec.

[PASSED] T1.1 - GET /health Endpoint
         - Returns status 200 OK with valid ISO timestamp and uptime stats.
[PASSED] T1.2 - Auth: User Registration
         - Registers participant role users; enforces unique email constraint and minimum 8-char 
           password policy. Validates password hashing using Argon2id algorithm (64MB memory, 
           3 iterations, 4 parallelism).
[PASSED] T1.3 - Auth: Password Policy Validation
         - Rejects short/weak passwords with HTTP 400 Bad Request and descriptive validation payload.
[PASSED] T1.4 - Auth: Login & Dual-JWT Token Provisioning
         - Authenticates valid credentials; returns short-lived (15m) JWT access token and 30d 
           HTTP-Only refresh token. Rejects invalid credentials with HTTP 401 Unauthorized.
[PASSED] T1.5 - Auth: User Profile & Session Inspection
         - GET /auth/me returns current user context with role claims and strips sensitive 
           passwordHash fields from response payload.
[PASSED] T1.6 - Auth: Protected Endpoint Guards
         - Unauthenticated requests to protected endpoints return HTTP 401 Unauthorized.
[PASSED] T1.7 - Events: Event Creation & Management
         - Organizers and admins can create events with registration/submission timelines, 
           team size constraints, and custom prize tracks.
[PASSED] T1.8 - Events: Public Event Listing & Detail Inspection
         - Unauthenticated public users can browse active and past hackathon events with metadata.
[PASSED] T1.9 - Events: RBAC Enforcement for Event Creation
         - Participants and judges attempting event creation are blocked with HTTP 403 Forbidden.
[PASSED] T1.10 - Teams: Team Formation & Unique Invite Code Generation
          - Participants can form teams for open events; auto-generates 12-character alphanumeric 
            unique invite codes.
[PASSED] T1.11 - Teams: Team Member Inspection & Detail Hydration
          - Returns full team roster including leaderId, members list, and current status.
[PASSED] T1.12 - Teams: Duplicate Event Registration Prevention
          - Rejects attempts by a participant to create or join multiple teams in the same event 
            with HTTP 409 Conflict.
[PASSED] T1.13 - API Documentation: OpenAPI 3.0 Specification
          - GET /api/openapi.json exposes complete valid JSON schema detailing all endpoints, 
            request/response structures, and security schemes.

SUITE T2: RUBRIC MANAGEMENT, JUDGING WORKFLOW & SCORING ENGINE
----------------------------------------------------------------------------------------------------
Objective: Validate rubric setup, judge invite tokens, round-robin workload distribution, score 
submission, cross-judge Z-Score normalization, and result visibility gating.

[PASSED] T2.1 - Rubric: Multi-Criteria Rubric Configuration
         - Organizers can create weighted criteria rubrics (e.g., Innovation, Execution, Pitch) 
           with individual maxScore and weight attributes; automatically calculates totalWeight.
[PASSED] T2.2 - Rubric: Rubric Inspection Endpoint
         - Retrieves full criterion definitions by rubric ID.
[PASSED] T2.3 - Rubric: RBAC Protection for Rubrics
         - Non-organizer roles are blocked from creating or modifying rubrics (HTTP 403/400).
[PASSED] T2.4 - Judging: Judge Invite Token Generation
         - Organizers can create multi-use, expiring invite tokens for streamlined judge onboarding.
[PASSED] T2.5 - Judging: Bulk Round-Robin Judge Assignment
         - Evenly distributes projects among available judges while executing conflict-of-interest 
           guards (disqualifying judges from scoring projects authored by their own team).
[PASSED] T2.6 - Judging: Judge Personal Roster & Assignments
         - Judges can fetch assigned project queue filtered by pending vs completed status.
[PASSED] T2.7 - Judging: Organizer Progress Tracking
         - Organizers can inspect real-time judging progress metrics across all assigned projects.
[PASSED] T2.8 - Scoring: Multi-Criteria Judge Score Submission
         - Assigned judges submit raw scores and inline comments per criterion; system computes 
           weighted raw scores and percentage normalized scores (0-100 scale).
[PASSED] T2.9 - Scoring: Cross-Judge Z-Score Normalization
         - Statistical algorithm computes per-judge mean (μ_j) and standard deviation (σ_j), 
           transforming scores into z-scores: z_ij = (S_ij - μ_j) / σ_j. Clamps normalized values 
           to 0-100 scale, successfully removing judge bias (lenient vs. harsh judges).
[PASSED] T2.10 - Results: Unrevealed Winner Gating
          - Participants/public cannot access ranked judging results before official reveal 
            (HTTP 403 Forbidden); admins retain immediate access.

SUITE T3: PUBLIC GALLERY, ANTI-ABUSE VOTING & COMMUNITY ENGAGEMENT
----------------------------------------------------------------------------------------------------
Objective: Validate public gallery browsing with seeded shuffle, search filtering, SHA-256 IP 
salt anti-gaming vote enforcement, comment moderation, and audit logging.

[PASSED] T3.1 - Gallery: Public Project Showcase
         - Displays submitted projects for active events, filtering out hidden/draft projects.
[PASSED] T3.2 - Gallery: Seeded PRNG Shuffle Fairness
         - URL seed parameter (`?seed=12345`) delivers deterministic pseudo-random project ordering, 
           preventing top-of-list exposure bias across different browser sessions.
[PASSED] T3.3 - Gallery: Text Search Filtering
         - Supports full-text search across project titles, descriptions, and technology tags.
[PASSED] T3.4 - Voting: Anti-Abuse Vote Casting
         - Authenticated users can cast public votes; system records SHA-256 IP-Event salt hash 
           to protect voter privacy while preventing multi-account network abuse.
[PASSED] T3.5 - Voting: Single Vote Constraint
         - Rejects second vote attempt by the same user/IP on the same project with HTTP 409.
[PASSED] T3.6 - Voting: Vote Count Privacy Gating
         - Hides raw vote counts from the public until results are officially revealed by organizers.
[PASSED] T3.7 - Engagement: Community Project Commenting
         - Logged-in users can post constructive project feedback up to 2,000 characters.
[PASSED] T3.8 - Engagement: Public Comment Retrieval
         - Unauthenticated users can view public comment threads on projects.
[PASSED] T3.9 - Engagement: Comment Moderation & Flagging
         - Users can flag objectionable comments; automatic threshold flags trigger moderator review.
[PASSED] T3.10 - Governance: Immutable Audit Log Recording
          - Organizers can review immutable audit trail tracking state-changing events (e.g., 
            `score.submitted`, `results.revealed`, `event.updated`); blocks participant access.

         - Organizers can export full project submission metadata as structured CSV files.

         - Judges can perform head-to-head project comparisons with 1-5 confidence scores.

[PASSED] T4.9 - Bradley-Terry: Next Uncompared Pair Generator
